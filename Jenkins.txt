Answer:
Pipeline as Code in Jenkins means defining the CI/CD pipeline using code instead of configuring it manually through the UI. 
This is done using a Jenkinsfile, which is stored in a version control system like Git. 
It allows us to reuse, version, and automate pipeline execution consistently.

Q3. What stages do you use in your CI/CD pipeline?
Answer:
In my CI/CD pipeline, code is pushed to GitHub which triggers the pipeline. 
The application is built using Maven and tested. I perform code quality analysis using SonarQube and security scanning using OWASP. 
Then I build a Docker image and scan it using Trivy before pushing it to a registry. 
Infrastructure is provisioned using Terraform with tfsec scanning. Finally, the application is deployed to EKS using Kubernetes manifests,

Q4. How do you trigger a pipeline automatically on code push?
Answer:
To trigger a pipeline automatically on code push, we configure webhooks in GitHub. 
Whenever a developer pushes code to the repository, GitHub sends a webhook event to the CI tool like Jenkins, 
which triggers the pipeline automatically.

Q5. How do you store credentials securely in Jenkins?
Answer:
Credentials in Jenkins are stored securely using the Credentials Manager under Manage Jenkins. 
We can add different types of credentials such as username/password, SSH keys, or tokens. 
Each credential is assigned a unique credential ID, which can be used in pipelines to securely access them. 
In pipelines, credentials are accessed using constructs like withCredentials, 
ensuring they are not exposed in logs. This helps avoid hardcoding sensitive data and improves security.

Q6. How do you manage secrets in CI/CD?
Answer:
Secrets in CI/CD can be managed using tools like HashiCorp Vault, AWS Secrets Manager, or Jenkins Credentials Manager. 
These tools securely store sensitive data such as passwords and API keys. AWS KMS is used to encrypt and decrypt secrets. 
Secrets are not hardcoded in the code; instead, they are injected into pipelines at runtime using environment variables or secure mechanisms, 
and retrieved from secret management systems like Vault.

Q7. What is a Quality Gate?
Answer:
Quality Gate is used in CI/CD pipelines to ensure code quality before proceeding to the next stages. 
It defines conditions such as code coverage, bugs, and vulnerabilities. 
After running code analysis using tools like SonarQube, the Quality Gate evaluates the results and gives a pass or fail status. 
If the code passes, the pipeline continues; if it fails, the pipeline stops and developers are required to fix the issues.

Q8. How does SonarQube fail the pipeline when quality gate fails?
Answer:
SonarQube fails the pipeline by evaluating the Quality Gate status after code analysis. 
Once the scan is completed, the CI/CD pipeline checks the Quality Gate result using a step like waitForQualityGate. 
If the Quality Gate status is failed, the pipeline is automatically aborted, 
and further stages are not executed. This ensures only quality-approved code is deployed.

Q9. What does waitForQualityGate do in the pipeline?"
Answer:
The waitForQualityGate step in a pipeline is used to pause the pipeline execution until SonarQube completes the code analysis and returns the Quality Gate result. 
It checks whether the Quality Gate status is pass or fail. If the Quality Gate passes, the pipeline continues to the next stages. 
If it fails, the pipeline is aborted, ensuring that only quality-approved code is deployed.

Q34. What is the difference between Continuous Delivery and Continuous Deployment?
Answer:

Continuous Delivery
Code changes are automatically built, tested, and prepared for release
Deployment to production requires manual approval
Ensures the application is always in a deployable state

Example:
Pipeline runs → build + test + deploy to staging → manual approval → production

Continuous Deployment
Code changes are automatically built, tested, and deployed to production
No manual intervention
Every successful change goes directly to production

Pipeline runs → build + test → automatically deployed to production

Q35. How do you trigger a pipeline only for a specific branch?
Answer:
Jenkins pipeline triggers based on the branch where the commit happens, 
and using when { branch 'branch-name' }, we can control which stages should run for that particular branch, 
while other stages will be skipped.

pipeline {
    agent any

    stages {

        stage('Checkout') {
            steps {
                git branch: 'main', url: 'https://github.com/example/repo.git'
            }
        }
        stage('Build') {
            when {
                branch 'main'
            }
            steps {
                sh 'mvn clean package'
            }
        }

        stage('Test') {
            when {
                branch 'master'
            }
            steps {
                sh 'mvn test'
            }
        }
    }

Q36. How do you ignore pushes from certain branches?

pipeline {

        }
    }
}

Q41. What is the difference between master and slave configuration?
Answer:
In Jenkins, the architecture follows a Master-Agent (formerly Master-Slave) model where responsibilities are divided between the controller and worker nodes.

Master (Controller)
Manages the Jenkins UI and configuration
Schedules and assigns jobs to agents
Maintains JENKINS_HOME and job configurations
Does not ideally run heavy build workloads

Slave (Agent)
Executes the actual build, test, and deployment tasks
Connects to the master via SSH.
Can be configured with specific labels (e.g., dev, test)
Helps in scaling and distributing workloads

Q58. What is concurrency issue in pipelines?
Answer:
A concurrency issue in pipelines occurs when multiple pipeline executions run at the same time and interfere with each other,

Q59. How do you calculate approvals before production?
Answer:
Before deploying to production, approvals are handled using manual approval gates in the pipeline, 
based on predefined rules like environment criticality, change impact, and organizational policies.

How Approvals Are Decided

Based on Environment Criticality
Dev/Test → No approval required
Staging → Optional approval
Production → Mandatory approval

Based on Change Type
Minor changes → Single approval
Major changes (infra / DB / security) → Multiple approvals
