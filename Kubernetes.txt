Q6. How do you troubleshoot a pod in CrashLoopBackOff?
Answer:
When a pod is in CrashLoopBackOff, it means the container is repeatedly crashing and Kubernetes is restarting it.
First, I check the pod status using: kubectl get pods, This helps identify the pod-name and restart count.
Next, I run:kubectl describe pod <pod-name>. This shows events and possible errors such as image pull issues, configuration problems, or resource limits.
Then I check container logs using: kubectl logs <pod-name>.
If the pod restarted, I check previous logs using: kubectl logs <pod-name> --previous
Common causes for CrashLoopBackOff include incorrect environment variables, misconfigured ConfigMaps or Secrets, application errors, or resource issues such as OOMKilled due to insufficient memory limits.

Q9. What does Pod NotReady state mean?
Answer:
Pod NotReady means the pod is running but it is not ready to serve traffic.
This usually happens when the readiness probe fails, indicating that the application inside the container is not yet ready to handle requests.
While the pod is in NotReady state, Kubernetes removes it from the Service endpoints, so it will not receive traffic until the readiness probe succeeds.

Q12. Readiness & Liveness probes?
Answer:
Readiness and Liveness probes are health checks used by Kubernetes to monitor container health

Readiness probes: Readiness Probe checks whether the container is ready to serve traffic. If the readiness probe fails, Kubernetes removes the pod from the Service endpoints, so it will not receive traffic until it becomes ready.

Liveness Probes: Liveness Probe checks whether the application inside the container is still running properly. If the liveness probe fails, Kubernetes restarts the container automatically using kubelet.  

Q13. What is Blue-Green deployment?
Answer: 
Blue-Green deployment is a release strategy where two identical environments are maintained, called Blue and Green.
The Blue environment represents the current production version, while the Green environment contains the new version of the application.
Once the Green deployment is verified and running correctly, traffic is switched from the Blue environment to the Green environment.
In Kubernetes, this is commonly implemented by having two deployments with different labels and updating the Service selector to route traffic from the Blue pods to the Green pods.
This approach minimizes downtime and allows quick rollback if issues occur.

Q15. What are the core components of Kubernetes?
Answer:
Kubernetes architecture consists of two main parts: Control Plane and Worker Nodes.
The Control Plane manages the cluster and includes components such as:
API Server – the entry point for all Kubernetes commands and communication between components.
Scheduler – assigns newly created pods to worker nodes based on available resources.
Controller Manager – runs controllers that ensure the cluster maintains the desired state, such as maintaining the required number of pods.
etcd – a distributed key-value store that stores all cluster data and configuration.
The Worker Nodes run the application workloads and include:
kubelet – an agent that communicates with the API server and ensures containers are running in the pods.
kube-proxy – manages networking rules and enables communication between services and pods.
Container Runtime – responsible for pulling images and running containers.
Finally, applications run inside Pods, which are the smallest deployable units in Kubernetes.

Q24. Can we attach PV/PVC to a Deployment?
Answer:
Yes, we can attach a PersistentVolumeClaim (PVC) to a Deployment. 
The PVC is mounted as a volume inside the pod, allowing containers to store data outside the pod. 
This ensures that the data persists even if the pod is deleted or restarted.
However, when using Deployments with multiple replicas, the storage access mode must support shared access such as ReadWriteMany. 
Otherwise, if the volume supports only ReadWriteOnce, only one pod can mount it at a time.

Deployments use a single PVC because all pods are created from the same template and share the same volume definition. 
Deployments are designed for stateless applications where pods are interchangeable. 
StatefulSets, on the other hand, use volumeClaimTemplates to automatically create a unique PVC for each pod, 
which is required for stateful applications like databases.

Q25. Can we create StatefulSet without PV/PVC?

StatefulSets are typically used for stateful applications that require persistent storage. 
If no persistent volumes are attached, the data will be stored inside the container filesystem and will be lost when the pod is deleted or restarted.

Q27. How does traffic flow from domain → Ingress → Service → Pod?
Answer:
When a user accesses an application using a domain name, the DNS resolves the domain to the external load balancer. 
The load balancer forwards the request to the Ingress Controller, which reads the Ingress rules and routes traffic based on host or path rules.
The Ingress then forwards the request to the appropriate Kubernetes Service, which load balances the request to one of the backend Pods. 
Finally, the request reaches the container running the application inside the pod.

Q28. What are Kubernetes Services?
Answer:
Kubernetes Service is an abstraction that provides a stable network endpoint to access a set of Pods.
Since Pods are ephemeral and their IP addresses change when they are recreated, a Service provides a stable IP address and DNS name to access those Pods.
Services also perform load balancing, distributing traffic across multiple Pods.

Q29. What is the difference between ClusterIP, NodePort, and LoadBalancer services?
Answer:
Kubernetes provides different types of Services to expose applications.
ClusterIP is the default service type that exposes the application internally within the cluster using a stable virtual IP address.
NodePort exposes the service on a specific port on each node, allowing external users to access the application using the Node IP and NodePort.
LoadBalancer creates an external load balancer provided by the cloud platform, which exposes the service to the internet and distributes traffic to the backend pods.

Q33. How pods communicate?
Answer:
In Kubernetes, each Pod receives a unique IP address in a flat network, which allows Pods to communicate directly with each other across the cluster. 
However, Pods are ephemeral and their IP addresses can change when they are recreated. 
Therefore, instead of using Pod IPs directly, applications usually communicate through Kubernetes Services, 
which provide a stable IP address and DNS name and load balance traffic to the backend Pods.

Q34. What is a headless service?
Answer:
A Headless Service is a Kubernetes service that does not have a ClusterIP. Instead of load balancing traffic, 
it returns the IP addresses of individual Pods, allowing clients to communicate directly with specific Pods. 
It is commonly used with StatefulSets to provide stable network identities.

Q38. How does Horizontal Pod Autoscaler work?
Answer:
Horizontal Pod Autoscaler (HPA) is a Kubernetes feature that automatically scales the number of pods in a deployment based on resource utilization such as CPU or memory.
HPA monitors metrics from the pods using the Kubernetes Metrics Server. It compares the current resource usage with the target utilization defined in the HPA configuration.
If the resource usage exceeds the target threshold, Kubernetes increases the number of pod replicas. If the usage decreases, it reduces the number of replicas.

Q40. What happens when a node goes into NotReady state?
Answer:
When a node goes into a NotReady state, it means the Kubernetes control plane cannot communicate with the kubelet on that worker node. 
In this situation, the Node Controller marks the node as NotReady and the scheduler stops placing new pods on that node.
If the node remains unreachable for a certain period (typically around 5 minutes),
Kubernetes evicts the pods running on that node. The controllers such as Deployments or ReplicaSets then recreate those pods, 
and the scheduler schedules them on other healthy nodes in the cluster.

Q41. Pod in Pending state?
Answer:
A Pod is in Pending state when it has been accepted by the Kubernetes API server but has not yet been scheduled to run on a node. 
This usually happens when the scheduler cannot find a suitable node to run the pod.
Common reasons include insufficient CPU or memory resources, unsatisfied node selectors or affinity rules, taints and tolerations restrictions,
 or unavailable Persistent Volumes required by the pod.
